为什么会有这个结果

网络计算量47×512 + 512×256 + 256×128 + 128×12 = 189,440 MACs（0.38 MFLOPs）
4080S 理论计算时间≈ 0.0095 µs
实测 GPU 延迟≈ 30 µs
开销占比99.9%
一次 CUDA 内核启动（20–30 µs）比整个网络的计算量大 3000 倍。CPU 侧理论 7.6 µs、实测 13 µs，总数仍低于 GPU 的启动开销。

方法（这部分决定结论可不可信）

  • 预热 100–200 次后才计时 —— 排除首次调用的内核编译/上下文开销
  • CUDA Event 计时 + synchronize；另做 wall-clock 双口径对照
  • 输入张量一次分配、循环内复用 —— 不把分配开销算进延迟
  • ONNX Runtime 用 io_binding，输入输出常驻显存 —— 不把 H2D 拷贝算进去
  • 报 p50 / p95 / p99 / max / σ，而不是只报均值；隐含上限 = 1000 / p99

结论与边界

  • 小模型实时推理：CPU 胜。 batch=1 时 ONNX Runtime + CPU 为 13 µs，是 GPU 方案的 1/3，且抖动最小（σ=2 µs）。
  • 部署别直跑 TorchScript。 同机同网络下 0.299 ms vs ONNX Runtime 0.013 ms——每调用开销 0.3 ms，是推理本身的 23 倍。
  • 控制环看抖动，不看均值。 偶发长尾才是真机上"动作不平滑"的来源。
  • 既有工程得到印证。 ORT-CPU 13 µs 只占 50 Hz 控制预算（20 ms）的 0.065%，说明真机延迟来自 CAN 下发、IMU 采样与调度抖动，而非模型推理。
  • 边界：结论仅限小模型。 上到 VLA / 视觉 backbone 时算力重新成为瓶颈，GPU（+TensorRT）才会回本。

一句话版（面试可用）

对 19 万参数的四足策略网络做了四后端横向对比（PyTorch JIT / ONNX Runtime × CPU / GPU），自建测量脚本（双口径计时、预热隔离、张量复用、io_binding 免 H2D），并做 batch 1→128 扫描定位交叉点。

发现：batch=1 时 GPU 的 99.9% 延迟是内核启动开销（30 µs vs 0.01 µs 计算），ORT-CPU 反而最快（13 µs、抖动 2 µs）；交叉点在 batch 8–32，batch 128 时 GPU 快 2.6 倍；TorchScript 每调用开销 0.3 ms，是推理本身的 23 倍。

该结论支撑了树莓派 5 上 50 Hz 部署的选型（推理仅占预算 0.065%）。

口径说明：以上为本机（RTX 4080 SUPER）实测数据。"树莓派 5 / 50 Hz" 为既有工程事实，与本次延迟数据相互印证，并非本实验的测试环境。
